## 1. はじめに：なぜ「プログラムが速いかどうか」を判断するのは難しいのか？

大学院の研究やシミュレーション、データ解析で「プログラムを C++ や Python で書き、GPU で動かしてみた」とします。
実行時間を測ると **「10 秒」** でした。

ここで、指導教員や共同研究者からこう尋ねられたらどう答えるでしょうか？

> **「この 10 秒は、ハードウェアの性能を限界まで使い切った結果の 10 秒なのか？  
> それとも、書き方を工夫すれば 0.1 秒（100 倍高速）になる余地がある 10 秒なのか？」**

多くの大学院生はここで言葉に詰まります。なぜなら、**「このハードウェアなら、この計算は原理的に何秒で終わるはずなのか」という絶対的な基準（ものさし）** を持っていないからです。

### 工場の比喩で考える
コンピュータの動作は「組み立て工場」によく似ています：
- **メモリ（RAM / VRAM）**: 部品を保管してある「倉庫」と、それを運ぶ「ベルトコンベア」
- **演算器（CPU / GPU コア）**: 部品を組み立てる「職人（作業員）」

プログラムが遅いとき、原因は大きく 2 つしかありません：
1. **ベルトコンベアが遅すぎて、職人が部品の到着を手持ち無沙汰で待っている（メモリ律速）**
2. **部品は山ほど届いているが、職人の手が追いつかずに作業が詰まっている（演算律速）**

もし原因が 1（部品待ち）なのに、職人を 100 人増やしても（＝より高価な GPU を買ったりコア数を増やしても）、部品が届くペースは変わらないため 1 秒も速くなりません。
**「いま何がボトルネックになっていて、どこまで速くできる限界なのか？」を一目で視覚的に診断するツール**、それこそが本稿で解説する **「Roofline Model（ルーフラインモデル）」** です。

## 2. 論文の背景：なぜ 2009 年にこのモデルが必要とされたのか？

この論文の共著者の一人である **David Patterson（デイビッド・パターソン）教授** は、計算機科学の最高栄誉である **チューリング賞** を受賞した伝説的計算機科学者であり、世界中の大学院生が読む名著『パターソン＆ヘネシー（パタヘネ本）』の著者です。

2000 年代中盤、コンピュータの世界で巨大なパラダイムシフトが起きました：
- **クロック周波数の頭打ち**: 消費電力と発熱の限界により、CPU の動作クロック（GHz）をこれ以上引き上げられなくなった。
- **マルチコア・GPU 時代の到来**: 1 個のコアを速くする代わりに、コアを 4 個、8 個、数千個（GPU）と並列に並べる時代に突入した。
- **「Memory Wall（メモリの壁）」の深刻化**: 演算器の計算能力は毎年爆発的に伸びる一方、メモリからデータを取ってくるスピード（帯域幅）の伸びは緩やかで、その格差が何十倍にも開いてしまった。

この結果、プログラマは「ハードウェアの構造を理解しないと、全く性能が出せない」という深い絶望に直面しました。これに対しパターソン教授らは、**「専門家でなくても、直感的にハードウェアの限界と最適化指針がわかる視覚的モデル」** として 2009 年に Roofline Model を提案したのです。

## 3. Roofline Model の核心：たった 2 つの軸で世界を見る

Roofline Model は、プログラムの性能を **2 つのパラメータ** だけで表現します。

### 概念 ①：演算強度（Operational Intensity）― プログラムの「体質」

プログラムが「メモリからデータを 1 バイト読み書きするごとに、何回の計算（演算）を行うか」を表す指標です。

$$\text{演算強度 } I = \frac{\text{総演算回数 [Operations または FLOPs]}}{\text{総メモリアクセス量 [Bytes]}} \quad [\text{Ops/Byte}]$$

* **演算強度が低いプログラム（例: $I = 0.1 \sim 1$）**:
  - 配列のコピー、ベクトル加算（$z[i] = x[i] + y[i]$）
  - 「8 バイトの数値を 2 つ読んで（16B）、1 回足し算して（1 Op）、8 バイト書き込む（8B）」$\implies 1 \text{ Op} \div 24 \text{ Bytes} \approx 0.04 \text{ Ops/Byte}$
  - **特徴**: とにかくメモリの読み書きばかりで、計算自体は一瞬で終わる。
* **演算強度が高いプログラム（例: $I = 50 \sim 200$）**:
  - 行列積（GEMM）、3次元流体シミュレーション、N体問題、多分岐正規表現マッチ
  - 一度読み込んだデータをレジスタやキャッシュに保持し、何十回・何百回も使い回して計算する。
  - **特徴**: メモリの読み書き量に対して、計算密度が非常に高い。

> **ポイント**: 演算強度は、ハードウェアではなく **「あなたが書いたアルゴリズム・コード」によって決まる固有の性質（体質）** です。

---

### 概念 ②：達成性能（Performance）― 実際の「処理スピード」

プログラムが、そのハードウェア上で 1 秒間に何回演算をこなせたかを表すスループット（処理能力）です。

$$P = \frac{\text{総演算回数 [Operations]}}{\text{実行時間 [Seconds]}} \quad [\text{Giga-Ops/sec または GFLOPS}]$$

---

### なぜグラフが「折れた屋根（Roofline）」の形になるのか？

ハードウェアの物理スペックには、絶対に破れない **2 つの限界（天井）** があります：

1. **メモリ帯域幅の天井 ($B_{\text{peak}}$ [GB/s])**:
   メモリからデータを送り出せる物理的な最大スピード。
   プログラムの性能は、$B_{\text{peak}} \times I$（帯域幅 $\times$ 演算強度）を超えることは絶対にできない。
2. **ピーク演算性能の天井 ($P_{\text{peak}}$ [GFLOPS または Giga-Ops/s])**:
   CPU や GPU の全コアが、クロックごとに 100% 休みなく計算し続けたときの物理的最大スピード。

この 2 つの制約を同時に満たす必要があるため、達成可能な最大性能 $P_{\text{roof}}$ は次のような **「折れ線（屋根の形）」** になります：

$$P_{\text{roof}}(I) = \min\left( P_{\text{peak}}, \; B_{\text{peak}} \times I \right)$$

これを両対数グラフ（log-log プロット）で描いたものが、世界中で使われている **Roofline グラフ** です。

```
達成性能 P [GFLOPS]
  ^
  │                      Peak Compute Performance (演算限界の天井)
  │                      ════════════════════════════════════════════
  │                     /
  │                    / 傾き = Peak Bandwidth (メモリ帯域幅)
  │                   /
  │                  /
  │                 /    ★ Knee Point (屈曲点 / リッジ点)
  │                /
  │   メモリ律速   /           演算律速 (Compute-bound)
  │ (Memory-bound)/
  └──────────────┴─────────────────────────────────────────────────> 演算強度 I [Ops/Byte]
                 I_knee
```

## 4. グラフの読み方とボトルネックの特定

Roofline グラフは、**屈曲点（Knee Point）** を境に世界が真っ二つに分かれます。

### 屈曲点（Knee Point）とは？
斜めの屋根と水平の屋根が交差するポイントです：
$$I_{\text{knee}} = \frac{P_{\text{peak}} \text{ (ピーク演算性能)}}{B_{\text{peak}} \text{ (ピークメモリ帯域)}}$$

たとえば、最新 GPU である **NVIDIA GeForce RTX 5090** の場合：
- ピーク整数演算能力: 約 $100 \text{ TIPS}$（$100 \times 10^{12} \text{ Ops/s}$）
- ピークメモリ帯域: $1,792 \text{ GB/s}$（GDDR7）
- **屈曲点 $I_{\text{knee}} = \frac{100 \times 10^{12}}{1.792 \times 10^{12}} \approx 55.8 \text{ Ops/Byte}$**

この「55.8」という数値が、この GPU における運命の分水嶺です。

---

### ① 斜めの屋根の下：メモリ律速（Memory-bound）領域 ($I < I_{\text{knee}}$)

あなたのプログラムの演算強度が 55.8 未満（たとえば $I = 5$）の場合、プログラムは **斜めの屋根** の下に位置します。

* **状態**: 演算器（職人）は 90% 以上の時間、メモリ（ベルトコンベア）からデータが届くのを待って遊んでいます。
* **特徴**:
  - プログラムの性能は、メモリ帯域幅に完全に比例します。
  - コアクロックを上げても、コア数を増やしても、性能はピクリとも向上しません。
* **最適化の処方箋**:
  - 演算を減らそうとするのは無意味（すでにコアは暇だから）。
  - **メモリアクセスを徹底的に削る**（キャッシュに乗るようにループを分割する、データ構造を圧縮する、不要な読み込みを排除する）。
  - つまり、**グラフ上で点を「右（演算強度が高い方向）」へ移動させる努力** が必要です。

---

### ② 水平の屋根の下：演算律速（Compute-bound）領域 ($I > I_{\text{knee}}$)

あなたのプログラムの演算強度が 55.8 以上（たとえば $I = 150$）の場合、プログラムは **水平の平らな屋根** の下に位置します。

* **状態**: メモリからのデータ供給は十分に間に合っており、GPU の演算ユニット（ALU/FPU）がフル稼働しています。
* **特徴**:
  - メモリ帯域を強化しても速くなりません。
  - より速いコア、より多くのコアを与えることで、性能がリニアに向上します。
* **最適化の処方箋**:
  - SIMD / AVX 命令や Tensor コア、FMA（積和演算）命令を使い、1 サイクルあたりにこなせる演算数を増やす。
  - 分岐命令（if 文のバラつき）を減らし、演算パイプラインのストールを防ぐ。

## 5. 実践：自分のプログラムをどうやって高速化するか？

プログラムの実測値を Roofline グラフにプロットしたとき、点は **必ず屋根の下（内側）のどこか** に着地します（屋根を超えることは物理法則上不可能です）。

```
達成性能 P
  ^
  │                      ════════════════════════════════════════════
  │                     /                      ▲ [天井へ押し上げる]
  │                    /        ● 実測点 B    │ (パイプライン最適化/並列化)
  │                   /          (Compute)     ▼
  │                  /
  │      ● 実測点 A /
  │       (Memory) /
  │         ───>  /  [右へシフトさせる]
  │   (キャッシュ活用/データ削減)
  └──────────────┴─────────────────────────────────────────────────> 演算強度 I
```

### パターン A：点が「斜めの屋根」の下で、屋根のすぐ近くにある
- **診断**: おめでとうございます。あなたのプログラムはメモリ帯域を 100% 使い切っており、**これ以上コードをいじっても速くなりません（すでに理論限界）**。
- **次の手**: アルゴリズム自体を変更して演算強度を右にシフトさせるか、より帯域の広いハードウェア（HBM メモリ搭載機など）に移行するしかありません。

### パターン B：点が「屋根」から遥か下の地面近くに落ちている
- **診断**: 最もよくあるケースです。ハードウェアの能力の数 % 〜 10% 程度しか出せていません。
- **原因の究明**:
  1. **並列度不足**: スレッド数が少なすぎて、多数のコアが眠っている。
  2. **メモリアクセスの非効率**: キャッシュに全くヒットせず、細切れに DRAM を叩いている（コアレスドアクセスの失敗）。
  3. **ワープダイバージェンス**: スレッドごとに if 文の分岐先がバラバラで、直列化（シリアライズ）されている。

## 6. 本プロジェクト（GPU 正規表現マッチング）での具体例

本リポジトリで取り組んでいる「GPU 上での Thompson NFA による大容量 Wikipedia 検索（Sprint 001〜003）」に、この Roofline Model を当てはめてみましょう。

### 1. メモリ転送の限界計算
- 対象データ: `enwik8`（約 95.9 MB）
- RTX 5090 のメモリ帯域: $1,792 \text{ GB/s}$
- **テキストをメモリから全ロードする最小時間**:
  $$T_{\text{min}} = \frac{0.0959 \text{ GB}}{1792 \text{ GB/s}} \approx 0.0000535 \text{ 秒} = 0.0535 \text{ ms}$$

### 2. 現実の実測値との比較
- 実測の GPU 実行時間: **約 35 ms 〜 500 ms**（パターンにより異なる）
- 単純なメモリ読み出し（0.05ms）に比べ、**実測は 700 倍〜 10,000 倍の時間がかかっています**。
- **Roofline 的結論**:
  本処理はテキストを垂れ流すだけの処理（Memory-bound）では決してなく、**1 文字読むごとに NFA 状態遷移・訪間フラグ管理・リスト操作という複雑な計算を何十回も繰り返す「Compute & Latency-bound」な処理** であることが数学的に裏付けられます。

### 3. Sprint 002 で実証された「逆転現象」のメカニズム
Sprint 002 では、正規表現の状態数 $|Q|$ を増やしていくと、並列度最大のはずの **GPU Line (LPC=1)** よりも、1 スレッドで 8 行をまとめて処理する **Chunked-Static (LPC=8)** の方が **1.30 倍高速になる** という現象が観測されました。

Roofline Model の観点から見ると、この理由は極めて明快です：
- **GPU Line**:
  1 行（115文字）終わるたびにスレッドが破棄されるため、状態配列（`visited[256]` 等）のキャッシュが毎行冷え切る（Cold Cache）。実効的なメモリアクセス量（L1/レジスタ外へのアクセス）が増大し、**点が下方に押し下げられる**。
- **Chunked-Static**:
  1 スレッドが同じ作業領域（L1 キャッシュやレジスタ）を使い回して 8 行連続で処理する（**時間的局所性: Cache Warmth**）。
  DRAM への不要な往復が消え、演算強度が右へシフトし、実効性能が **Compute の天井（屋根）近くまで押し上げられた** のです。

## 7. まとめ：研究者が持っておくべき「ものさし」

Roofline Model が世界中の計算機科学者・HPC 技術者に愛されている理由は、**「不毛な最適化の泥沼」から救ってくれるから** です。

| 疑問 | Roofline Model が教えてくれる答え |
|---|---|
| **「いまのコードは速いのか？」** | 実測点が屋根に近ければ、それが物理限界。これ以上コードを弄る必要はない。 |
| **「なぜ並列化したのに速くならないのか？」** | メモリ律速領域にいる場合、コアを増やしても帯域がボトルネックで頭打ちになる。 |
| **「次に何を改善すべきか？」** | メモリ律速ならキャッシュ活用・データ圧縮。演算律速ならベクトル化・分岐削減。 |

大学院での研究において、シミュレーションや大規模データ処理を高速化する際は、やみくもにコードを書き直す前に、まず **「自分の計算の演算強度 $I$ はどこにあるのか？」** を計算してみてください。それだけで、進むべき最適化の道筋がクリアに見えてくるはずです。
