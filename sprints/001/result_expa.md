# 実験 A / A' 個別レポート: enwik8 におけるチャンク並列化手法の比較と LPC スイープ分析

**日付**: 2026-08-08  
**対象データセット**: `enwik8` (95,909,488 文字, 831,111 行)  
**実行環境**: Docker コンテナ内 (`re_exp_env_gpu`, NVIDIA CUDA 11.8 / RTX 5090)  
**計測条件**: 30 種の正規表現パターン × 3 回実行の平均値  

---

## 1. 概要

本レポートでは、大容量テキスト（`enwik8`）に対する GPU 正規表現マッチングにおいて、以下の3つの手法およびそのパラメータ（`LINES_PER_CHUNK`, LPC）が CPU前処理および GPU実行時間に与える影響を分析・考察します。

### 比較手法の定義
* **GPU Line**: 1 行 = 1 GPU スレッド（最大並列度）
* **Chunked-Static**: LPC 行（デフォルト=8行）= 1 GPU スレッド（固定行数チャンク）
* **Chunked-Dynamic**: 目標文字数相当 = 1 GPU スレッド（文字数均等化チャンク）

### 2.2 実験 A の詳細考察

#### ① CPU前処理時間の差: GPU Line (+2.1ms) vs Chunked-Static
* **原因**: 転送するオフセット情報の件数が LPC 倍（= 8倍）異なることによる。
  * **GPU Line**: 全行の開始・終了位置（831,111 件 × 2 × 8B ≈ **12.65 MB**）を転送。
  * **Chunked-Static**: チャンク境界位置（103,889 件 × 2 × 8B ≈ **1.58 MB**）のみ転送。
* チャンク化により転送データ量が **1/8** に削減されるため、Chunked-Static の CPU 前処理が約 2.1ms 高速化します。

#### ② CPU前処理時間の差: Chunked-Dynamic (+3.3ms) vs Chunked-Static
* **原因**: Dynamic 固有の **$O(n_{lines})$ 文字数均等化スキャン** が追加されるため。
* 全 831,111 行の文字数を CPU で順次累積ループ処理するため、前処理コストが大きく増加します。

#### ③ GPU実行時間の差: GPU Line (40.4ms) < Chunked-Static (42.3ms)
* 一見、スレッド数が少ない Chunked-Static の方が速そうに見えますが、**「直列処理の損」** が影響しています。
  * **GPU Line (8スレッド並列)**: 8行の完了時間 $\approx \max(\text{8行の長さ})$
  * **Chunked-Static (1スレッド直列)**: 8行の完了時間 $\approx \sum(\text{8行の長さ})$
* スレッド数が 1/8 に減るメリット（wave 数減）と、1スレッドの処理時間が約 3 倍に伸びるデメリットが相殺し、わずかに GPU Line が勝つ結果となりました。

## 3. 実験 A': LPC スイープによる粒度とパフォーマンスの仮説検証

### 3.1 仮説と目的
* **仮説**: 「1スレッドが直列に処理する行数（LPC）を小さく（1〜4）すれば、直列処理の損が減り、GPU 実行時間が短くなるのではないか？」
* **目的**: LPC = 1, 2, 4, 8 における Static / Dynamic の挙動をコンテナ内環境で比較検証する。

### 3.2 計測結果（CPU前処理 / GPU実行 / 合計 内訳）

LPC の値（1, 2, 4, 8）ごとに CPU 前処理時間 (Pre)、GPU 実行時間 (GPU)、合計時間 (Tot) をミリ秒単位で整理しました。

| LPC | **Chunked-Static Pre (ms)** | **Chunked-Static GPU (ms)** | **Chunked-Static Tot (ms)** | **Chunked-Dynamic Pre (ms)** | **Chunked-Dynamic GPU (ms)** | **Chunked-Dynamic Tot (ms)** |
|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| **1** | 19.75 | 44.39 | 64.15 | 23.35 | 58.58 | 81.93 |
| **2** | 20.89 | 47.75 | 68.64 | 22.98 | 55.96 | 78.94 |
| **4** | 20.96 | 44.79 | 65.75 | 22.25 | 48.38 | 70.63 |
| **8** | **19.38** | **41.63** | **61.01** | **22.41** | **46.08** | **68.49** |
| *GPU Line (参考)* | *21.94* | *40.39* | *63.99* | — | — | — |

> **ポイント**:
> 1. **CPU 前処理**: どの LPC においても Static は約 19.4〜20.9ms、Dynamic は約 22.3〜23.4ms で安定（Dynamic の $O(n_{lines})$ スキャンコスト +3.0ms 差）。
> 2. **GPU 実行**: Static, Dynamic ともに **LPC = 1 で最遅（Static: 44.4ms, Dynamic: 58.6ms）** であり、**LPC = 8 で最速（Static: 41.6ms, Dynamic: 46.1ms）** となる。

### 3.3 実験 A' の詳細考察: なぜ仮説は棄却されたか？

実測の結果、**LPC = 1 が最遅であり、LPC = 8 が最速** となり、「直列処理を減らすため LPC を小さくすれば速くなる」という仮説は棄却されました。

CPU前処理とGPU実行時間それぞれにおいて以下の要因が働いています。

#### ① CPU 前処理時間に対する LPC の影響
* **Static (19.4〜20.9ms)**: チャンク数の差（831K個 → 104K個）によるオフセット配列サイズの差は軽微で、テキスト全体の `\n` スキャン時間（約 19ms）が支配的です。
* **Dynamic (22.3〜23.4ms)**: 全行の文字数を順次加算する $O(n_{lines})$ ループが追加されるため、Static より一貫して約 **+3ms** 重くなります。

#### ② GPU 実行時間に対する LPC の影響（固定コストの希釈効果）
1. **スレッド/ワープ起動・管理の固定コスト (Launch Overhead)**:
   - スレッドID計算・範囲チェック・境界ロード等の固定処理が、**LPC = 1（83万スレッド）では83万回** 発生します。
   - **LPC = 8（10万スレッド）では10万回** に激減し、1つのスレッド起動コストに対して8行分処理するため、**オーバーヘッドの密度が 1/8 に希釈** されます。
2. **VRAM 帯域とキャッシュ再利用効率 (Memory & Cache Traffic)**:
   - LPC = 8 では、1つのスレッドが L1/L2 キャッシュやレジスタ領域（`clist`, `nlist`, `visited`）を維持したまま 8 行分を連続ループ処理するため、メモリ空間の再利用効率が高まります。

---

## 4. 結論とまとめ

1. **CPU 前処理**: Chunked-Static はオフセット転送量が GPU Line の 1/8 になるため最速 (19.8ms)。Dynamic は CPU での $O(n_{lines})$ スキャンが入るため最遅 (23.2ms)。
2. **GPU 実行**: enwik8 のように均一な長さに近い文章では、LPC = 8 において「スレッド管理オーバーヘッドの希釈」と「キャッシュ効率」が極めて高く働き、GPU Line に匹敵する高速性を達成する。
3. **LPC 依存性**: LPC を 1 に近づけると管理オーバーヘッドが肥大化して悪化する。直列処理のコストと管理オーバーヘッドのバランスが最適になる点が LPC = 8 付近に存在する。
